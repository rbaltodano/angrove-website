Better Sources Beat a Bigger Model.

A larger model in a smaller file looked promising. Comparing factual errors, phone memory, and source retrieval changed where I put the engineering effort.

Ryan Baltodano·October 20, 2026·4 min read

PrismML’s Ternary Bonsai 2 squeezes a 9-billion-parameter model into 2.4 GB by storing each weight as one of three values. That is smaller than the 4-billion-parameter-class Gemma 4 E4B that Angrove ships. If the bigger model held up, the phone could get a smarter model with a smaller model file. File size alone would not establish its runtime memory use. I added a llama.cpp runtime beside LiteRT-LM so either model can run through the same app pipeline, then wrote 40 harder questions to compare them: precise distinctions, false premises, exact history, and ten multi-turn exchanges.

Bonsai 9B scored lower than E4B, and its misses were confident wrong facts rather than weak reasoning: it called 451 the year of the First Council of Constantinople, and credited the Athanasian Creed to Athanasius. A prompt written for it made no difference. The same model compressed less gets those facts back, reaching 37 at 3 bits, which points to extreme compression as a contributor to the factual loss in these runs. On the base iPhone 17, though, the phone ran out of memory loading it.

Giving the model the right source

Most wrong answers were facts the model had to remember. So I tested the other way to supply facts: hand the model the passage that answers the question. With a correct passage, every model scored 39 or 40, so the gap between them nearly disappeared. Real retrieval is harder. Searching Wikipedia with the raw question often returned the wrong pages, so the model now writes short keyword queries, and a 22-million-parameter reranker reads the question beside each paragraph and keeps the ones that answer it.

What it changed: Gemma 4 E4B stays the model. I am building an optional Wikipedia search, off by default, that runs only when Angrove’s own Library has nothing on a question. The model writes a few search keywords, which are the only thing that leaves the phone; a 43 MB on-device reranker chooses the paragraphs; and the answer lists the Wikipedia articles used and the sources they cite. The comparison above used a shared set of fetched Wikipedia results. In the first end-to-end working version on the Mac, it raised E4B from 31 to 34 at about 11 seconds per answer. Reranking Angrove’s own Library helped less, because the Library lacks many historical facts, which points to adding a public-domain reference work next.

Limits of these numbers

One greedy run per configuration; most runs on a Mac, with the iPhone table as marked. The scorer checks patterns, so reading the answers moved a few results in both directions. The hard questions were also used to build the search pipeline, so its gains still need confirming on fresh questions. The Wikipedia search is not yet in a released build.
